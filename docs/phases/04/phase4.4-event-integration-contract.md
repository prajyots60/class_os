## 1. Executive Summary & Scope Boundary

### 1.1 Purpose
This document establishes the **authoritative, frozen architectural contract** for **Phase 4.4 — Domain Event Integration & Projections** of CoachingOS.

Phase 4.1 implemented **Announcement Engine Core**.  
Phase 4.2 implemented **Notification Core & In-App Engine**.  
Phase 4.3 implemented **Child Activity Timeline Engine**.  
Phase 4.4 defines the **Domain Event Integration, Recipient Resolution, Projection Orchestration, and Event-Driven Boundary** connecting upstream business domains (`Academics`, `Billing`, `Identity`, `Communication`) to the `Notification` and `Activity` projection engines.

### 1.2 Strict Scope Constraints for Phase 4.4
- **ARCHITECTURE & CONTRACT FREEZE ONLY**: Zero production event subscriber code, worker loops, REST API routes, UI components, or external queues are constructed in Phase 4.4.
- **NO DATABASE DRIFT**: No Prisma schema modifications or PostgreSQL migrations are introduced in Phase 4.4.
- **NO EXTERNAL INFRASTRUCTURE DEPENDENCIES**: Redis, BullMQ, Sentry, Trigger.dev, and third-party SaaS queue dependencies are strictly prohibited per ADR-0003.
- **RESERVED FOR SUBPHASE 4.4.1**: Production event bus subscribers, projection handlers, and event listeners will be implemented in subphase Phase 4.4.1.

## 3. Canonical Event Envelope Specification

All domain events emitted across CoachingOS MUST adhere strictly to the frozen `DomainEventEnvelope` interface:

```typescript
export interface DomainEventEnvelope<TType extends string = string, TPayload = unknown> {
  readonly eventId: string;         // Globally unique UUID v4 generated by producer
  readonly eventType: TType;        // Dot-separated event taxonomy string (e.g. 'academics.attendance.recorded')
  readonly instituteId: string;     // Authoritative Tenant ID derived from server context
  readonly occurredAt: string;      // ISO 8601 string timestamp of business event occurrence
  readonly payload: TPayload;       // Immutable event payload containing domain facts
  readonly metadata?: {
    readonly requestId?: string;    // Server-generated correlation ID
    readonly actorUserId?: string;  // User ID of staff/system initiating the action
  };
}
```

### Envelope Invariants
1. `eventId`: MUST be a non-empty UUID v4 generated by the event producer prior to publishing. It serves as the primary idempotency seed.
2. `instituteId`: MUST be verified server-side. Events containing missing or null `instituteId` MUST be rejected immediately by event subscribers.
3. `occurredAt`: MUST be an ISO 8601 UTC string timestamp (`YYYY-MM-DDTHH:mm:ss.sssZ`).

## 8. Recipient Resolution Contract

### 8.1 Recipient Resolution Invariants
1. **Target Identity Isolation**: Notifications MUST be addressed to a specific authenticated `User` (`recipientUserId`).
2. **Parent Resolution**: When an event affects a student, parent `userId`s MUST be resolved using active `StudentLink` $\rightarrow$ `ChildProfile` $\rightarrow$ `ParentIdentity` $\rightarrow$ `User` linkages.
3. **Inactive User Filter**: Resolved recipients who are suspended (`status === 'suspended'`) or deleted (`deletedAt !== null`) MUST be filtered out prior to notification creation.
4. **Zero-Recipient Handling**: If an event resolves to zero active recipients (e.g. unlinked student), the system MUST log a structured warning (`communication.projection.zero_recipients`) and gracefully complete the Activity projection without throwing an exception.

---

## 9. Student Context Contract

### 9.1 Student Identity Requirements
1. Activity entries are strictly attached to a single `studentId`.
2. Batch-level events (`academics.homework.published`, `academics.test.published`, `communication.announcement.published` targeting a batch) MUST resolve all active batch enrollments (`Enrollment` status `active`) to obtain individual `studentId`s.
3. If an event cannot be associated with a valid `studentId` (e.g., institute-wide announcement for staff only), the Activity projection MUST be skipped while allowing the Notification projection to proceed.

---

## 10. Tenant Context & Security Propagation Contract

### 10.1 Tenancy Security Invariants
1. **Event Tenant Authority**: Every domain event envelope MUST contain `instituteId`.
2. **Cross-Tenant Verification**: Prior to creating a Notification or Activity projection, the projection service MUST verify that the target student and recipient user belong strictly to `event.instituteId`.
3. **Tenant Mismatch Failure**: If `student.instituteId !== event.instituteId` or `user.instituteId !== event.instituteId`, the projection MUST be aborted immediately with a `security.tenant_mismatch` audit log error.
4. **Server Context Preservation**: Client request headers, query parameters, or body overrides MUST NEVER be trusted during event projection processing.

## 11. Event Identity & Idempotency Strategy

### 11.1 Deterministic Projection Idempotency Seeds

To guarantee idempotent consumer execution during event replays or retries:

#### Notification Idempotency Identity
```text
notification_idempotency_key = SHA256(event.instituteId + ":" + event.eventId + ":" + recipientUserId + ":" + projectionType)
```

#### Activity Idempotency Identity
```text
activity_idempotency_key = SHA256(event.instituteId + ":" + event.eventId + ":" + studentId + ":" + activityEventType)
```

### 11.2 Database Uniqueness Safeguard
- `notifications`: `@@unique([institute_id, recipient_user_id, idempotency_key])`
- `activities`: `@@unique([institute_id, student_id, idempotency_key])`
- Application-level `findBySourceIdempotencyKey` checks are backed by PostgreSQL unique constraints to handle high-concurrency event projections atomically.

---

## 12. Concurrent Delivery Semantics & Race Condition Prevention

```text
Worker Thread A ──► Event X ──┐
                             ├──► PostgreSQL Primary Key / Unique Constraint Upsert
Worker Thread B ──► Event X ──┘
                             │
                             └──► Exactly 1 Notification / Activity Record Created
```

1. Concurrent execution of duplicate event projections (e.g. Worker A and Worker B processing Event X simultaneously) is handled via PostgreSQL atomic `upsert` semantics.
2. In the event of a unique constraint collision (`P2002`), the repository catches the error, re-queries the existing record by idempotency key, and returns the existing entity cleanly without throwing an unhandled exception.

---

## 13. At-Least-Once Delivery Semantics

1. The CoachingOS event pipeline operates under **At-Least-Once Delivery** guarantees.
2. Subscribers MUST treat all event handlers as **100% IDEMPOTENT**. Replaying an event 100 times MUST yield identical database state as processing it once.

## 14. Transaction Boundaries

### 14.1 Post-Commit Event Emission Rule
- Upstream producers (`Academics`, `Billing`, `Communication`) MUST emit domain events **ONLY AFTER** the primary database transaction has successfully committed.
- **Strict Invariant**: Domain events MUST NEVER be emitted inside an open Prisma `$transaction` block. Emitting events inside open transactions risks publishing uncommitted state if the transaction subsequently rolls back.

```text
  ┌──────────────────────────────────────────────────────────┐
  │ 1. Open Prisma Transaction ($transaction)                │
  │    - Update Invoice / Record Payment / Save Attendance   │
  │ 2. Commit Transaction                                    │
  └────────────────────────────┬─────────────────────────────┘
                               │ Transaction Committed Successfully
                               ▼
  ┌──────────────────────────────────────────────────────────┐
  │ 3. Post-Commit Domain Event Emission                     │
  │    - eventBus.publish('billing.payment.recorded', event) │
  └──────────────────────────────────────────────────────────┘
```

## 15. Failure Isolation Contract

```text
                               Domain Event Emitted
                                        │
                    ┌───────────────────┴───────────────────┐
                    ▼                                       ▼
        Notification Projection                 Activity Projection
                    │                                       │
            ┌───────┴───────┐                       ┌───────┴───────┐
            ▼               ▼                       ▼               ▼
        Success          Failed                  Success          Failed
       (Logged)    (Isolated & Retried)         (Logged)    (Isolated & Retried)
```

1. **Projection Isolation**: `NotificationProjectionService` and `ActivityProjectionService` MUST execute in independent error-handling try-catch scopes.
2. Failure during Notification projection MUST NOT roll back or corrupt Activity projection.
3. Failure during Activity projection MUST NOT roll back or corrupt Notification projection.
4. Projection failures MUST NOT affect the upstream producer's already-committed business state.

---

## 16. Retry Semantics & Exponential Backoff

1. Transient projection errors (e.g., temporary database connection timeouts) are retried using exponential backoff:
   - **Attempt 1**: Immediate execution.
   - **Attempt 2**: Delay 1,000ms.
   - **Attempt 3**: Delay 5,000ms.
   - **Max Attempts**: 3 retries.
2. Permanent validation errors (e.g., tenant mismatch, malformed payload, invalid student ID) MUST NOT be retried. They are logged as dead-letter validation failures and terminated immediately.

---

## 17. Observability & Event Tracing Contract

All event integration operations MUST log structured Pino events following `domain.action.result` naming conventions:

- `communication.event.received`: Emitted when an event subscriber receives a domain event.
- `communication.projection.started`: Emitted when projection handler begins processing.
- `communication.projection.succeeded`: Emitted on successful Notification/Activity creation.
- `communication.projection.duplicate`: Emitted when idempotency key prevents duplicate creation.
- `communication.projection.tenant_mismatch`: Emitted when tenant security validation fails.
- `communication.projection.zero_recipients`: Emitted when event targets no active recipients.
- `communication.projection.failed`: Emitted on unhandled projection errors.

### PII & Credential Redaction Invariant
- Passwords, session tokens, auth cookies, database connection strings, and raw credit card numbers MUST NEVER be logged.
- Every event log MUST include `requestId`, `eventId`, and `instituteId`.

## 18. Security Threat Model & Defense Matrix

| Threat ID | Threat Scenario | Attack Vector | Security Defense Invariant |
| :--- | :--- | :--- | :--- |
| **T-EVT-001** | Forged Event Tenant ID | Attacker injects foreign `instituteId` into payload | Event subscriber validates `instituteId` against target student/user DB tenant |
| **T-EVT-002** | Cross-Tenant Student Reference | Event references Student ID belonging to Institute B | Projection verifies `student.instituteId === event.instituteId`. Rejects on mismatch |
| **T-EVT-003** | Duplicate Event Replay | Attacker replays historical event payload | Idempotency key uniqueness check drops duplicate event replays cleanly |
| **T-EVT-004** | Concurrent Projection Storm | Concurrent event workers process same event | PostgreSQL atomic unique constraint (`upsert`) prevents duplicate rows |
| **T-EVT-005** | Malformed Event Payload | Payload missing required fields or incorrect types | Zod validator / Zod event schema validates payload prior to projection |
| **T-EVT-006** | Unknown Event Type | Attacker emits unregistered event type | Event dispatcher ignores unhandled event types with structured warning log |
| **T-EVT-007** | Event Schema Version Mismatch | Producer payload version mismatch | Consumer handles optional fields safely; ignores unknown fields |
| **T-EVT-008** | Projection Handler Crash | Database failure during projection | Handled in try-catch boundary; producer business transaction remains intact |
| **T-EVT-009** | Recipient Resolution Failure | Target parent user deleted or unlinked | Gracefully logs `zero_recipients` warning; completes Activity projection |
| **T-EVT-010** | Announcement Batch Mismatch | Batch announcement sent to wrong institute batch | Enforces `batch.instituteId === event.instituteId` prior to notification resolution |
| **T-EVT-011** | Event Missing Student Context | Event payload lacks required `studentId` | Skips Activity projection; logs structured warning; completes Notification |
| **T-EVT-012** | Cross-Tenant Notification Leak | Notification sent to user in another tenant | Recipient user tenant verified (`user.instituteId === event.instituteId`) |

## 19. Event Versioning & Schema Evolution Strategy

1. **Backward Compatibility**: Event payload schemas MUST evolve additively. Fields MUST NOT be renamed or deleted in minor version updates.
2. **Optional New Fields**: New fields added to event payloads MUST be optional (`field?: string`).
3. **Event Version Property**: Every event envelope contains `eventVersion` (Default `'1.0'`). Consumers inspect `eventVersion` to handle legacy vs modern payload structures.
